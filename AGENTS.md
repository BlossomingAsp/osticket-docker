# osTicket docker image and compose project

Self-hosted osTicket helpdesk stack: a custom PHP 8.3 Apache image + MariaDB, orchestrated with docker-compose.

This file is the agent/dev runbook. The user-facing guide lives in `README.md` — keep user-relevant install/config/operating docs there and reserve this file for development, release workflow, and implementation gotchas.

## Commands
- First run: `./install.sh` — asks auto-setup vs manual wizard, creates `.env` (mode 600), builds the image, and starts the stack. Non-interactive: `-y --auto` (auto-setup) or `-y --manual`. Manual alternative: `cp .env.example .env`, set the DB passwords (and `OSTICKET_*` if wanted), then `docker compose up -d --build`
- Bootstrap install from a release: `bash <(curl -sSL https://github.com/BlossomingAsp/osticket-docker/releases/latest/download/get-osticket.sh)` — interactive (prompts for passwords, port, helpdesk details). `get-osticket.sh` downloads the release source tarball and runs its `install.sh`; `OSTICKET_RELEASE` pins a tag. Process substitution (`bash <(curl ...)`) is REQUIRED so stdin stays a terminal — piped installs (`curl ... | sh`) are deliberately rejected: they consume stdin so `install.sh` can't prompt, and `install.sh` dies with a pointer to the correct one-liner unless `-y` is given. It extracts into `./osticket-docker/` (`OSTICKET_DIR` overrides) and keeps the files so the stack can be managed afterwards — do NOT assume the files are in a temp dir or that a local copy exists for cleanup. If the CWD isn't writable it falls back to `mktemp -d` (cleaned up on exit). The repo is PUBLIC, so the unauthenticated one-liner works for anyone. (If it ever goes private again, `git clone` or export `GH_TOKEN` — the bootstrap and its downloads honor it.)
- Channels: `get-osticket.sh` supports `OSTICKET_CHANNEL=stable|experimental` (default `stable`). `experimental` resolves the latest GitHub **prerelease** (falling back to stable when none exists yet). Experimental features are developed on the `experimental` branch and cut as prerelease tags from it, e.g. `v1.1.0-exp.1` (`gh release create v1.1.0-exp.1 --prerelease --target experimental` or the API with `"prerelease": true, "target_commitish": "experimental"`).
- Discord ticket bot (experimental, `docker/discord-bot/`): a `discord-bot` compose service. Users post `!ticket` messages (Key: Value lines; name/email/message required) in a configured channel → `docker/discord-bot/osticket_api.py` creates the ticket via `POST /api/tickets.json` (API key auth) → `docker/discord-bot/db.py` records the Discord message ↔ ticket mapping in the `ost_discord_ticket_map` table (auto-created on start) → the bot reacts to the message and, on a `POLL_INTERVAL` loop, updates the reaction when the ticket status changes (emoji map from `STATUS_EMOJIS`, matched case-insensitively against the status `name`, which is language-dependent — for hu_HU use `{"Megnyit":"🟢",...}`). The osTicket API key must be created in the admin panel (Manage → API Keys) with IP `172.30.0.10` — osTicket binds API keys to an **exact** client IP (the lookup is `WHERE apikey=? AND ipaddr=<REMOTE_ADDR>`), so the discord-bot service is pinned to that static IP on a dedicated compose subnet (`172.30.0.0/24`); a CIDR like `0.0.0.0/0` will NOT authenticate. There is no API endpoint to read ticket status, so the bot reads `ost_ticket`/`ost_ticket_status` directly from MariaDB (same credentials as the stack). Bot exits cleanly (exit 0, `restart: on-failure`) when `DISCORD_BOT_TOKEN`/`DISCORD_CHANNEL_ID` are unset so users without Discord aren't crash-looped.
- Release workflow: stable — `gh release create vX.Y.Z --generate-notes` (or the GitHub API with a `GITHUB_TOKEN`); attach `get-osticket.sh` as an asset so the one-liner above resolves. Experimental — same, but from the `experimental` branch with `--prerelease`. **Channel baking**: the asset uploaded to a release controls the one-liner's default channel. Stable releases ship `get-osticket.sh` as-is (`DEFAULT_CHANNEL=stable`). Experimental releases must upload a version with the channel baked to experimental: `sed 's/DEFAULT_CHANNEL="${DEFAULT_CHANNEL:-stable}"/DEFAULT_CHANNEL=experimental/' get-osticket.sh` — so the one-liner on an experimental release page installs the experimental prerelease by default. Release bodies should point the one-liner at that release's asset URL (`.../releases/download/<TAG>/get-osticket.sh`) rather than `/releases/latest/` when the baked channel matters. The bootstrap also falls back to `DEFAULT_TAG` if `/releases/latest` isn't reachable.
- The GitHub token is stored in `.github_token` (gitignored, mode 600); read it with `TOKEN="$(cat .github_token)"` and `unset TOKEN` after use. It's the `ghp_...` classic token provided by the owner — treat it as a secret, never paste it into commit messages or the release body, and never `git add` it.
- Validate compose: `docker compose config`
- Update osTicket: `./update.sh` (queries the latest osTicket release from the GitHub API; bumps `OSTICKET_VERSION` in `.env` on approval and runs `docker compose up -d --build`). `install.sh` also checks for a newer release and offers to bump the version — the prompt is skipped with an explicit `-v`, when non-interactive, and in `--dry-run` (those only report availability, never modify `.env`).
- Discord bot setup: `./setup-discord-bot.sh` — interactive helper (experimental) that prompts for the bot token, channel ID, ticket command, osTicket API key, topic, channel field, poll interval, rate limit, status-emoji map, and fallback emoji, then writes only the `OSTICKET_DISCORD_*`/`OSTICKET_TOPIC_ID` keys into `.env` (`sed` replace or append) and offers to (re)start the `discord-bot` service. Flags: `-y`/`--yes` (non-interactive, keep current `.env` values), `-n`/`--no-start` (skip the restart prompt), `-h`/`--help`. Dies if `.env` is missing, docker/compose are absent, or (interactive mode) stdin isn't a terminal — same non-terminal rule as `install.sh`. It must NOT `source` the whole `.env` (unquoted values like `OSTICKET_OIDC_NAME=Pocket ID` would break the shell); it reads individual keys with `sed`/`env_get`. Avoid `${VAR:-{...}}` defaults containing braces — bash terminates the expansion at the first `}` and appends the rest literally (a default like `STATUS_EMOJIS` must be assigned via a separate `if [ -z ]` branch, not `${VAR:-{\"...\"}}`).
- Two install paths:
  - **Auto-setup** (`OSTICKET_AUTOINSTALL=1`): the entrypoint POSTs the official wizard on first boot (`prereq` → `config` → `install`) using `OSTICKET_*` vars (helpdesk name/email, language, timezone, admin account, DB creds), then provisions plugins + OAuth instances. No browser.
  - **Manual wizard**: browse to `http://localhost:8080/setup/` (DB host `db`, creds from `.env`). The entrypoint pre-creates `include/ost-config.php` from `setup/inc/ost-sampleconfig.php`, so the wizard form appears directly.
- After install, `docker/entrypoint.sh` auto-deletes `/var/www/html/setup` on next container start (only when `OSTINSTALLED` is TRUE) — no manual hardening step. Plugins/OAuth provisioning (`docker/provision.php`) also runs on every start after install.
- Check required PHP extensions: `docker compose exec osticket php -m`
- Rebuild after Dockerfile changes: `docker compose up -d --build`

## Gotchas
- The one-liner MUST be `bash <(curl -sSL ...)` (process substitution), never `curl ... | sh`. A pipe consumes stdin, so interactive prompts can't work. `install.sh` dies with a pointer to the correct one-liner when `ASK=1` and stdin isn't a terminal; `get-osticket.sh` refuses up front too. `-y` (non-interactive) still works in pipes/CI. Don't regress either check.
- Do NOT use the official `osticket/osticket` hub image; it is stale (PHP 7 era) and osTicket v1.18.4 requires PHP 8.2–8.4. Use the repo `Dockerfile`.
- Image is pinned to `php:8.3-apache-bookworm`. Do NOT unpin: default `php:8.3-apache` tracks Debian trixie, where `libc-client-dev` (needed to build the `imap` extension) no longer exists. `imap` is bundled in PHP 8.3 but moved to PECL in 8.4.
- DB must be MariaDB, not MySQL 8 — MySQL 8's `caching_sha2_password` auth breaks osTicket's installer.
- `include/` is a named volume (`osticket_data`), so `ost-config.php`, plugins, and language packs persist, but the volume shadows the image's `include/`: rebuilding the image does NOT update files already in the volume. Plugin files are therefore re-copied from `/opt/osticket-plugins` (in the image) into `include/plugins/` on every start, and language packs are re-copied from `/opt/osticket-i18n` into `include/i18n/` — they DO update on rebuild.
- osTicket version is `OSTICKET_VERSION` in `.env` (default `1.18.4`), passed as a build arg; PHP version is the base image tag in `Dockerfile`. Plugins come from osTicket-plugins 1.17.x pinned to commit `adfef05` (`PLUGINS_COMMIT` build arg), hydrated with composer deps at build time.
- Language packs: `OSTICKET_LANG` (build arg + env) is bundled at build time from `https://s3.amazonaws.com/downloads.osticket.com/lang/<minor>.x/<short>.phar` (short code = part before `_`, e.g. `hu` for `hu_HU`). The file is saved under the FULL code (`hu_HU.phar`) because `Internationalization::availableLanguages()` derives the language code from the phar basename (`basename($f,'.phar')`, `_` split, must exist as a key in `include/i18n/langs.php`); the official pack is only published under the short name. `en_US` ships as a directory and skips the download. Build hard-fails if the pack download fails.
- Why `system_language` was silently `en_US` (don't regress): the wizard's `Install::install()` (setup/inc/class.installer.php) only builds `new Internationalization($vars['lang_id'])` and never writes `system_language`; `Internationalization::__construct()` (class.i18n.php) only adds the requested lang to `$this->langs` when `getLanguageInfo()` finds an installed pack, so without the pack it stays `['en_US']` and `loadDefaultData()` writes `system_language=en_US` (class.i18n.php:143). With the pack present at install time this is fixed automatically; for existing installs `docker/provision.php` enforces `system_language = OSTICKET_LANG` on every start (declarative, like TRUSTED_PROXIES).
- The official hu_HU language pack's `queue.yaml` is defective: the root queues get a non-zero `parent_id` (queue 1 → parent 1, i.e. it points to itself; My Tickets/Closed point to Open instead of being roots). `CustomQueue::getHierarchicalQueues()` (include/class.queue.php) then recurses forever on the self-loop and `/scp/` dies with a memory-exhaustion 500 (`Allowed memory size exhausted ... class.orm.php`). Don't regress the fix: the image ships a corrected override at `docker/i18n/hu_HU/queue.yaml` staged into `/opt/osticket-i18n/<LANG>/` and synced into the `include/` volume by the entrypoint every start. osTicket's `DataTemplate` (include/class.i18n.php) prefers a directory (`include/i18n/<lang>/queue.yaml`) over the phar, so the override wins at install time without touching the phar. Belt-and-braces: `docker/provision.php` also repairs any circular/dangling queue `parent_id` on every start (a fresh `docker compose up -d` self-heals an existing install).

- Update checks (`install.sh` and `update.sh`) query the public `osTicket/osTicket` GitHub API for `releases/latest` (unauthenticated, rate-limited) and compare with `sort -V`. They must fail gracefully offline/rate-limited — never block install or update on a failed check.
- `OSTICKET_TRUSTED_PROXIES` (`.env`, optional) is injected into `include/ost-config.php`'s `TRUSTED_PROXIES` define on container start — set it (proxy IP/CIDR list) for reverse-proxy/HTTPS deployments. HTTPS detection needs no config: osTicket reads `X-Forwarded-Proto` directly.
- OAuth/OIDC: each configured provider (Pocket ID/Google/Discord) is one auth-oauth2 plugin instance, created by `docker/provision.php` via the plugin API (`PluginManager::install` + `addInstance`). Client secrets go through the plugin config form (encrypted). Redirect URI is always `<helpdesk URL>/api/auth/oauth2`; register it in each IdP app. Provider is only provisioned when its `CLIENT_ID` is non-empty.
- Plugin names in `OSTICKET_PLUGINS` are the image dir names `auth-oauth2`/`auth-2fa` (NOT `oauth2`/`2fa`) — the entrypoint copies `/opt/osticket-plugins/<name>` and provision.php installs by the same name.
- Provisioning pitfalls in `docker/provision.php` (all fixed, don't regress): it must run the full CLI bootstrap (`Bootstrap::loadConfig(); defineTables(TABLE_PREFIX); loadCode(); connect(); osTicket::start()`) — `require bootstrap.php` alone does NOT define `OSTINSTALLED` (only `include/class.cli.php` calls `loadConfig`); set `$_SERVER['REQUEST_METHOD']='POST'` or the config forms merge the empty saved config over your `$vars` (clientSecret validation fails); and do NOT re-fetch plugins via `PluginManager::allInstalled()` right after install/activate — osTicket's ORM caches query results so you get stale `isactive=0` rows, reuse the `ensure_plugin()` return values instead.
- `OSTICKET_AUTOINSTALL=1` requires `OSTICKET_ADMIN_PASSWORD` and `MARIADB_DATABASE/USER/PASSWORD` (passed to the osticket service); the four other required auto-setup fields (`OSTICKET_HELPDESK_NAME`, `OSTICKET_DEFAULT_EMAIL`, `OSTICKET_ADMIN_EMAIL`, `OSTICKET_ADMIN_USERNAME`) fall back to defaults when blank (`Help Desk`, `helpdesk@localhost`, `admin@localhost`, `admin1`) — applied both in `install.sh` and `docker/entrypoint.sh`. Admin username must not be `admin`/`admins`/`username`/`osticket`; admin email must differ from the default system email. The wizard install uses `prefix=ost_`, `dbhost=db`, timezone from `OSTICKET_TIMEZONE`.
- Secrets live in `.env` (gitignored); never commit it. Changes to `.env` require `docker compose up -d` to re-apply.

## Layout
- `docs/ARCHITECTURE.md` — the deep technical reference (components, env vars, data flows, known issues). README is the user guide; this file is the dev runbook; that file is the "how it all works" doc. Keep all three in sync when behaviour changes.
- `Dockerfile` — two stages: `plugin-builder` (php:8.3-cli-bookworm; downloads osTicket-plugins, runs `make.php hydrate`, keeps `auth-oauth2` + `auth-2fa` in `/opt/osticket-plugins/`) and the runtime image (php:8.3-apache-bookworm + osTicket extensions gd/gettext/imap/intl/mysqli/pdo_mysql/zip/apcu; OPcache tuned + `expose_php=Off` via `docker/php-opcache.ini`, Apache `ServerTokens Prod` via `docker/apache-security.conf`; app source from GitHub release zip; `OSTICKET_LANG` phar downloaded to `include/i18n/` + staged in `/opt/osticket-i18n/`; plugins + `docker/provision.php` copied in)
- `docker/entrypoint.sh` — pre-creates `ost-config.php`, auto-installs via wizard when `OSTICKET_AUTOINSTALL=1`, removes `/setup` when installed, injects `TRUSTED_PROXIES`, copies plugins + the language pack into the include volume, runs `/opt/osticket-provision.php`, execs `apache2-foreground`
- `docker/php-opcache.ini` — OPcache tuning (`memory_consumption=128`, `max_accelerated_files=10000`, `validate_timestamps=0`) + `expose_php=Off`; copied to `/usr/local/etc/php/conf.d/99-osticket-opcache.ini`. The base php image already loads the opcache extension (via `docker-php-ext-opcache.ini`), so this file must NOT add another `zend_extension` line (duplicate-load warning). `validate_timestamps=0` is safe because the entrypoint re-syncs plugins/language packs into the include volume BEFORE Apache starts, and `ost-config.php` is (re)written before first compile.
- `docker/apache-security.conf` — `ServerTokens Prod` + `ServerSignature Off`; enabled via `a2enconf zz-osticket-security` in the Dockerfile (the `zz-` prefix makes it load AFTER the base image's `security.conf`, whose `ServerTokens OS`/`ServerSignature On` would otherwise win).
- `docker/provision.php` — bootstraps osTicket (like `manage.php`) and uses `PluginManager::install()`/`addInstance()` to install/activate plugins and create the OAuth2 (Pocket ID/Google/Discord) + 2FA instances from `OSTICKET_*` env vars, and enforces `system_language = OSTICKET_LANG` on every start
- `install.sh` — mode question (`--auto`/`--manual`), prompts DB + auto-setup vars, writes `.env` (prompts, `-y` non-interactive, `--dry-run`), builds, starts
- `setup-discord-bot.sh` — interactive configurator for the discord-bot service (see Commands); writes `OSTICKET_DISCORD_*`/`OSTICKET_TOPIC_ID` into `.env`
- `docker-compose.yml` — `db` (mariadb:11.4, utf8mb4) + `osticket` (build: .), healthchecks + `depends_on`, all `OSTICKET_*`/`MARIADB_*` vars passed to the osticket service
- `.env.example` — config template documenting every variable
